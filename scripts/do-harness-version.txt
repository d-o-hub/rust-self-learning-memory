# do-harness CLI version contract — the single tracked reference for the harness
# binary this repository's agent workflow is validated against (issue #1247).
#
# This repository uses **only the latest upstream release**. `pin` and `validated_through`
# are therefore always the same number — the newest release published on
# https://github.com/d-o-hub/do-harness — and never a compatibility floor. Nothing here
# validates an older release.
#
# `pin` is what `scripts/check-do-harness-compat.sh` requires locally (>= pin; when the
# resolved binary is older, the probe says to install the pin rather than downgrade it) and
# what the `harness-compat` job in `.github/workflows/skill-evals.yml` downloads exactly,
# with the sha256 from the release's `checksums.txt`. AGENTS.md, HARNESS.md and the harness
# skill must name this same number — the probe fails if they name anything else.
#
# Both probes are recorded green against the published binary of the tracked version. The
# pack declares `inputs` on its sensors, so the floor that made this file necessary was
# 0.2.0: 0.1.0 has no such field and rejects the whole pack (`unknown field 'inputs',
# expected one of name, argv, retry, timeout, allow_failure, transient_exit_codes,
# when-changed`). That history is why the number is pinned at all; the policy since is
# simply "track the newest release".
#
# Raising this number is a deliberate change: install the new release, run
#   ./scripts/check-do-harness-compat.sh
# and record the output on the PR. Prose may not cite a version above this line.
#
# Note when validating an older release by hand anyway: `doctor` also checks the applied
# migrations of the workspace state database (`.do-harness/agent_state.db`). Against a
# database a *newer* harness has migrated, an older binary reports `doctor check failed:
# newer than this binary (23 applied, max 21)` — local state, not a property of this pack,
# and one more reason to run only the newest release.
pin = "0.4.6"
validated_through = "0.4.6"
